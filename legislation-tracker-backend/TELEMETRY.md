# Ingestion telemetry

This telemetry change is separate from the published bill-card dashboard. Reuses Django/DRF, PostgreSQL, Celery, Redis and existing staff cookie/CSRF authentication. No new dependencies.

`0008_discovery_run.py` adds discovery lifecycle records and an active-scope uniqueness constraint. It has been applied only by pytest to synthetic isolated test databases. Apply it to a chosen deployment database only through the normal authorized migration process. No existing/shared database was migrated during development.

Staff-only GET `/api/ingestion/telemetry/` returns scoped current work-item counts, runnable/scheduled pending counts, stale leases, latest work states, last successful work-item timestamp, last successful discovery timestamp and latest discovery-run state. It never creates state or dispatches tasks. Counts are observed reads, not a transactionally frozen global snapshot; the observation timestamp is explicit. Recent states are not an immutable event history. Null-Congress work is excluded from a Congress-scoped view. No full downstream-run correlation or completion percentage is provided.

Staff-only GET `/api/ingestion/source-readiness/` reads a cached inventory snapshot and SELECTs the current cursor/work revision basis to validate incremental readiness. The cache key includes federal jurisdiction, Congress and sorted HR/S types. It never contacts Congress.gov. Missing, incomplete or older-than-300-second snapshots return unavailable/null readiness counts. Frontend ages and expires accepted snapshots locally, too.

Explicit count-only command, requiring existing configured Congress.gov access:

```sh
rtk proxy python manage.py check_ingestion_readiness --congress 119 --bill-types hr s --json
```

Do not run this as part of deployment or UI rendering. It makes source GETs and local SELECTs and writes a telemetry cache snapshot only; no ingestion state/bill/work writes, imports or dispatches. Coverage is federal HR/S bill metadata only. Resolutions and updates to existing metadata are not counted as new bills. Complete enumeration validates source identities, pagination count stability and uniqueness. Max 80 pages/120 seconds; failures or rate limits terminate without retries and return incomplete/null counts. Source counts are observed inventory, not transactional upstream guarantees. Existing queued, processing, blocked or dead identities are excluded from missing_unqueued_metadata even if a different revision succeeded. Redis cache coalesces checks for 180 seconds and retains snapshots one hour; tests use local-memory cache. No source credentials are returned in diagnostics. Shared client transport diagnostics omit provider error bodies and credential-bearing exception strings.

The existing staff POST `/api/ingestion/poll-congress/` still accepts jurisdiction/Congress and returns task fields, now also run_id/status/coalesced. Scope is validated; unsupported jurisdiction/type parameters and noninteger Congress values are rejected. Optional Idempotency-Key header or idempotency_key body identifies retries. Same accepted key always replays that run; a different key during an active run returns409 and is not accepted. Global key conflicts return400. Terminal replay does not create a new run. A new key is required for a new request.

Claims use a scope-state row lock and a partial unique active-run constraint, shared by HTTP and Beat's existing poll_congress task. Pending/running claims have20-minute leases; abandoned claims become unknown, not succeeded. Page heartbeats and a locked check before durable work/cursor persistence fence expired or superseded claims. Manual publication uses transaction.on_commit; rollback never publishes. Broker ambiguity is recorded as unknown and503; this is not exactly-once publishing. A delivered task checks its pending claim; redelivery coalesces. Redis/Celery work dispatch, retry budgets and lease recovery are preserved.

Discovery succeeded means source enumeration and durable work persistence completed. Downstream tasks may still be queued, blocked, running or failed. Last successful work item is never called last completed run. Worker crashes may leave unknown discovery outcomes until reconciliation; no fabricated completion is inferred.

Validation uses mocked provider requests and synthetic SQLite/PostgreSQL databases, including real PostgreSQL concurrent claim races. No live source inventory or ingestion start was run. Operational screenshots use explicit HTTP fixtures. Main-dashboard original rollback remains controlled by its existing independent local flag; telemetry has its own flag.

Inventory semantics: missing_unqueued_metadata is a full-source historical metadata gap count, not readiness for incremental Start. ready_to_start is the observed distinct bill-identity count that would create new bill work in the next incremental poll; incomplete, stale or changed-basis observations return null. Start retains the existing cursor and five-minute overlap; historical gaps may be omitted. No cursor reset or backfill was added. Malformed, naive or future source timestamps make all inventory counts unavailable. Prepare requires a terminal refreshed snapshot with the exact accepted run ID.

Cache configuration: base settings use django.core.cache.backends.redis.RedisCache at REDIS_URL; dev and prod inherit it. Test/e2e explicitly override with LocMemCache and cannot prove cross-process sharing. Deployment must give the inventory command and HTTP workers the same Redis location/database and key configuration. No running deployment cache configuration is claimed here.

The isolated real-Redis cross-process regression is apps/ingestion/tests/test_cache_sharing.py. It can launch a dedicated Unix-socket native Redis with no TCP port/persistence, or use TELEMETRY_TEST_REDIS_URL=redis://127.0.0.1:15449/0 only for the externally owned dedicated test container. Each run has a unique key prefix; it deletes only its own snapshot/lock keys. It writes a synthetic snapshot through the actual management command in one process, reads SourceReadinessView in another and verifies cache.add scan-lock exclusion. The Redis-container route passed on this Mac; no shared Redis was contacted. The latest-only run feed may conservatively prevent Prepare when a newer scheduled run hides the accepted run; uncertain publication without an accepted ID also cannot enable Prepare. Retry preserves its key; no arbitrary latest run authorizes reset.

Incremental readiness is observed separately with the exact HR/S GET scope, fromDateTime formatted by the shared five-minute overlap helper, shared bill-list updateDateIncludingText precedence, shared timezone/date parsing and unknown-date sentinel. For each distinct source identity, the maximum observed source revision creates work only if no equal or newer kind=bill revision exists for that global dedupe_key. Existing metadata alone does not exclude it; existing equal/dead revisions are not automatic retries; newer revisions of active work count because Start creates them. The observer only reads source/DB and never imports tasks, persists rows, dispatches or changes cursors.

The response exposes discovery_basis (cursor_at, from_date_time, scope, work_revision_digest), discovery_checked_started_at/completed_at, discovery_source_complete and readiness_semantics. Basis includes all bill-work revisions whose keys share the Congress prefix (conservative invalidation); it is compared before/after the scan and again on every HTTP read. A changed cursor or revision set, incomplete/unstable pagination, budget exhaustion, invalid observation time or age over300seconds makes ready_to_start null. Full inventory gaps remain a separate observed metric. The management command shares an80-page/120-second budget across both scans. Newer remote source changes cannot be detected without a subsequent explicit source check; this is an observed count, not an atomic promise that Start will create exactly that many rows.

Verified cache setup used an already installed redis:7-alpine image, temporary container legislation-telemetry-redis-task8 on localhost15449, no persistent volume and no pull/install. The command-to-HTTP cross-process cache snapshot and cache.add scan-lock test passed. That verifies the existing RedisCache backend contract; deployment still must configure command/HTTP with the same Redis URL/database/key settings.
